## 3. Email breaker
- **What trips it** (`src/email.js` 120 to 136): over 7 days, once there are at least **200** `alert_email_sent` events, a bounce rate above **5%** or a complaint rate above **0.3%**. Verdict cached 10 minutes. Below 200 sends it never trips.
- **What it pauses:** every non-transactional email going through `sendEmailWithGuard()`. Separately, per-stream pauses (`stream_pauses`, `src/emailStreams.js`) act only with at least 1,000 delivered in 7 days (complaint 0.1%, hard bounce 2%, daily unsubscribe 0.5%).
- **Confirmations are not paused.** `isTransactional(stream)` (`src/emailCompliance.js:16`) skips the breaker (`email.js:249`), the stream pause (`:254`) and the Q1 send budget ("Transactional mail (verification, confirmations, the support reply) is never counted or blocked", `src/sendBudget.js:4`). The signup verification email is sent with `stream: 'transactional'` (`email.js:416`) through `ctx.waitUntil` (`src/index.js:3363`). **So S4's exemption part is already done.** What I did not check is a test that proves it end to end with the breaker tripped; I can add one in S4.
- **Daily ceiling on the current Resend plan: owner.** The repo does not record the plan or its daily limit, and I cannot read the Resend dashboard. If the account is on a plan with a daily cap (the free plan has one), that cap, not our code, decides how many confirmations go out in a surge. Please read it from Resend -> Settings -> Billing.
- **Surge of 500 signups in one hour:** the code sends one verification per signup, immediately, with no queue and no batching. 500 per hour is about 0.14 a second, far under any per-second API limit I know of, so **the code would delay none**; the only thing that could delay or drop them is a daily send cap or a per-second limit on the plan (both owner-readable, neither in the repo). The digest uses batches; the verification path does not.

## 4. Measurement (M1)
Read from code; a production check needs the admin secret (owner) and test signups, which I did not make.
- **What is stored.** Two parallel tags:
  - `attribution.js` (loaded on every page via `/brand/header.js`): `channel` = `utm_source` if present, else the referrer class (`search`, `social`, `email`, `other_site`, `direct`); `campaign` = `utm_campaign`; first touch per browser session, added to any `POST /api/signup` body by a fetch wrapper. Sanitized in the browser and again in `src/attribution.js`: lowercase, characters `[a-z0-9_-]` only, **channel 20 characters, campaign 16**. Anything else is **stripped, not mapped to `other`**.
  - `utm.js`: joins `utm_source`, `utm_campaign`, `utm_content` with `_` into one string (40 characters) and the signup keeps it in the event's `meta.utm`; `/admin/growth` shows it as "Tag" (`by_utm_last28`).
- **New values are not dropped.** There is no allowlist of channels, so `linkedin`, `press_aaa` (9), `vfr_ord_krk` (11), `producthunt` (11), `bluesky` all fit the length limits and are stored verbatim. `report_nov11` (12) and `launch_nov7` (11) fit the 16-character campaign limit. The Hub's convention `sale_check` (10) fits.
- **Gaps found:**
  1. **`utm_medium` is never read or stored anywhere** (searched `utm.js`, `attribution.js`, `src/attribution.js`, `src/growth.js`). The SOURCE_TAGS convention in S1 uses `utm_medium` (`post`, `comment`, `email`, `article`); it would be lost. This is the only real S1 code change.
  2. `utm.js` flattens source, campaign and content into one underscore string, so `linkedin` + `launch_nov7` reads `linkedin_launch_nov7`, indistinguishable from a source called `linkedin_launch`. The structured `signup_channel` / `signup_campaign` columns (N5) are the clean ones; use those for reports.
  3. A value is lost if it is over the limit (cut, not flagged) or has other characters (stripped). A tag with a dot or a space becomes a different tag.
- **What collapses to `direct`:** a visit with no `utm_source` and no referrer, or an in-site referrer. Mobile apps (LinkedIn, Reddit, Bluesky apps, email apps) often send no referrer, so **untagged posts will read as `direct`**; tagged links will not. `lnkd.in` is classed `other_site`, `t.co` and `ycombinator`/`producthunt` as `social`. Signups made without the browser wrapper (a different origin, a stripped session) show `unknown`/`direct`.
- **Entry pages:** `attribution.js` classes the landing by path: `/check` -> `check`, `/time-off*` -> `pto`, `/reports*` -> `report`, home, route pages, everything else `other`. The digest archive (`/digest`) falls in `other`, and I did not find a signup form on it, so there is nothing to tag there. Signups started on `/check` and `/time-off/<origin>` post to `/api/signup` and receive the wrapper's channel and campaign.
- **Not verified:** a live test with three new source values (S1's acceptance). It needs the owner to run it, or an approved `+alias` signup on production.

## 7. Calendar code
- **How `.ics` is made:** `buildIcs()` in `src/ptoCalendar.js:364`. One all-day event per plan block (`DTSTART;VALUE=DATE`, exclusive `DTEND`), `METHOD:PUBLISH`, `X-WR-CALNAME`, `TRANSP:TRANSPARENT`, a `URL` and a description linking the page. Served as an attachment from `/time-off.ics` (national, `src/index.js:5881`) and `/time-off/<origin>.ics` (`:5938`, regex `^/time-off/([a-z]{3})(\.ics)?$`).
- **Stable UIDs: yes.** `UID:${start}-${end}-${origin||'us'}@sparkfare.com`, so a block keeps its UID across refreshes. `DTSTAMP` is the request time (normal).
- **What is missing for a subscribable feed (S7):** no `REFRESH-INTERVAL` / `X-PUBLISHED-TTL`, no `webcal://` link, no `/time-off/2027.ics` or `/time-off/<origin>/2027.ics` route (the origin regex needs three letters, so `2027` would 404, and the feed route must come first), no feed-specific description or as-of date, no `utm_source=calendar` link, no aggregate request counter, and the response is `Content-Disposition: attachment` (a subscription URL should serve `text/calendar` inline). No `VALARM` exists, which matches the spec.
- **Existing national and per-origin files cover the default plan (through the planner's last day) and carry the budget in the URL; a 2027-only zero-PTO feed is a new plan variant, not a rename.**
