# N4 load test: the daily digest at scale (2026-10-24)

Addendum N, package N4 (ROADMAP step 152). Reproduce with `node --test tests/n4_capacity.test.js` (the 2,500-subscriber case prints its own line of queries, batch calls, wall time and CPU).

## What was found

The daily digest (`sendDailyAlerts`, the 08:00 UTC run) made about **11 D1 queries per subscriber**: two `CREATE TABLE IF NOT EXISTS` statements and a suppression lookup in the guarded send, a referral-code lookup and an Away Mode partner lookup while building the email, plus the delivery row (check, insert, update) and an event insert. Cloudflare's D1 limit is **1,000 queries per Worker invocation on Workers Paid (50 on Free)** (developers.cloudflare.com/d1/platform/limits, read 2026-10-24). So the digest stopped working at roughly **90 subscribers**: the tail of the list would have failed with a query-limit error. The first goal-ladder target is 100 confirmed subscribers by Nov 7.

## Method

A harness runs the real `sendDailyAlerts` against a real SQLite database with every migration applied, wrapped so each statement sent to D1 is counted. Resend is a stub that answers like the real API (single send and `/emails/batch`). Subscribers are spread across the 23 origins; every origin has three deals; production flags (`ENABLE_EMAIL_V2`, `ENABLE_DIGEST_SKIP_UNCHANGED`, `ENABLE_T3_REFERRALS`) are on. Wall time and CPU time are measured around the call in Node on a laptop (not the Workers runtime), so they are indications, not guarantees.

## Results

| Subscribers | Before: D1 queries | After: D1 queries | After: Resend calls | After: wall / CPU |
| --- | --- | --- | --- | --- |
| 100 | 1,096 (11.0 each) | **106** | 1 batch | 0.19 s / 0.25 s |
| 500 | not run (would be about 5,500) | **126** | 5 batches | 0.65 s / 0.77 s |
| 2,500 | not run (would be about 27,000) | **230** | 25 batches | 2.6 s / 2.8 s |

At 2,500 subscribers: 2,500 sent, 0 failed, 0 duplicate delivery keys, every subscriber emailed exactly once, 2,500 `alert_email_sent` events. A second run the same day sends nothing and makes under 30 queries.

Limits for reference (Cloudflare, read 2026-10-24): D1 queries per invocation 1,000 (Paid); subrequests per invocation 10,000 (Paid); CPU per cron invocation 30 seconds for crons that run more often than hourly and 15 minutes for hourly or less often (the daily digest is the second kind). 25 Resend calls and 230 queries are far inside all three.

## What changed

- Who was already sent today: one query (was one per subscriber).
- Pending delivery rows: one bulk insert per 500 (was one per subscriber).
- Last-sent date for skip-if-unchanged: one grouped query (was one per subscriber).
- The email is built per subscriber in memory; the Away Mode partner is picked once and referral codes are read in one query per batch (were one query each).
- Sending: `resend.batch.send` with 100 emails per call, `batchValidation: 'permissive'` (one bad address is reported by index and fails alone), and an `Idempotency-Key` derived from the date and the recipient list, so a retry of the same batch cannot double-send. If the batch call itself fails, that chunk falls back to one send per recipient.
- Results are written in bulk per chunk: statuses, `alert_email_sent` events. Failed recipients keep their own error text.
- The guard and suppression checks run once per batch (one query for the whole suppression list) instead of once per email.
- **Unchanged:** the email content (subject, HTML, text and the `List-Unsubscribe` headers are identical to the single-send path, tested for the v1 and v2 digests), the delivery-row idempotency, skip-if-unchanged, the sending guard, suppression handling, and the counts `sendDailyAlerts` returns.

## Not covered by this change

- **The 08:00 invocation does other work too** (watchlists, departing-soon, stress-valve, departure-briefing, retrospectives, pre-departure sequences, reconciliation, health checks). They share the same 1,000-query budget and each still makes several queries per row. They are small today (a handful of trips), but each should be given the same bulk treatment before they reach a few hundred rows. Logged as a follow-up, not done here.
- The Sunday newsletter already sends through the batch endpoint; its per-user lookups are not changed here.
- Real Workers CPU time can only be seen on a real run; the first live digest after this change is the check (the standup shows the sent count; `wrangler tail` shows errors).

## Indexes (migration 0033)

`events(ts)`, `events(event_type, ts)`, `users(verified_email, is_subscribed)`, `users(created_at)`, and `trips(user_id)` (already present in production under the same name). `EXPLAIN QUERY PLAN` for the standup's event counts, the growth report's confirmation count, the digest's recipient query, signups-per-week and trips-by-user now reports `SEARCH ... USING INDEX` / `COVERING INDEX` instead of a table scan (`tests/n4_capacity.test.js`).
